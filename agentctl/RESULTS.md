## S1 — dirty state の継承機構 (20/20)

一時 index に `git add -A` して `write-tree` + `commit-tree` で seed commit を作る方式。

```
親の (a) 追跡ファイル変更 / (b) staged / (c) 未追跡  → 子に byte 一致で伝播
親の (d) gitignore 対象                          → seed tree に不在 (共有側で扱う)
親の HEAD / status / .git/index mtime / stash ref → すべて不変
孫の seed は .agents/ を除外                      → 再帰安全
3way patch で子の成果を親の dirty tree へ還流      → 親の作業中状態は保持
```

**`git stash create` を棄却した数値:** git 2.53.0 の man は `git stash create [<message>]`。
`-u` は "only valid for push and save commands" と明記。未追跡ファイルが黙って落ちる。

## S1b — 対照と衝突経路 (6/6)

- **R5 解決 (対照つき):** worktree ごとの `info/exclude` は**効かない**。
  対照として `$GIT_COMMON_DIR/info/exclude` は効き、linked worktree にも届く。
  → `.gitignore` か共通 dir のみが正当な退避先。
- **衝突時:** `git apply --3way --check` が正しく拒否し、親のファイルは byte 一致のまま。
  衝突マーカーも `.rej` も残らない。
  なお素の `--3way` もこの例では部分適用しなかったため、`--check` ゲートは
  「必要性を実証済み」ではなく**予防的**。

## S3 — スロット調停と劣化検出 (PASS)

常駐サーバ (`llm-api.service`, `-c 32768 --parallel 2`, KV q8_0) に接続して測定。

```
単流 decode        24.70 t/s
2 並列 decode 合計  37.99 t/s  = 1.54 倍   (リポジトリ既測の上限 1.48 倍)
4 並列             peak slots 2、壁時計 22.22 t/s (2 並列 21.13 を下回らない)
llama プロセス      1 → 1 (増殖なし)
対照ドリフト        0.5% (24.60〜24.73)
劣化検出           閾値超過時に Degraded を送出、結果を返さない
```

### 測定系の誤りを 2 回踏んだ記録

**1 回目 — 指標の取り違え。** `総トークン / 壁時計時間` を「総合スループット」として
単流 17.88 t/s を得たが、真の decode は 24.9 t/s。prefill・HTTP・キュー待ちを
含んでいた。リポジトリの 1.48 倍は `S_TG` (生成のみ) 列の比であり、比較対象が
違っていた。サーバ報告の `predicted_per_second` に切り替えて解決。

**2 回目 — 設問が不成立。** 「4 並列は 2 並列を上回らない」を検証しようとしたが、
リポジトリの B=4 は **`--parallel 4`**、つまりサーバのスロット数の話。スロット 2 の
サーバにクライアント 4 並列を投げてもキューに並ぶだけでスロットは増えない。
検証には再起動が要り、それは常駐要件が禁じる。`decode_sum` も n ≤ スロット数で
しか意味を持たない (4 並列では同時実行していない 4 本を合算していた)。
**閾値を緩めず予測を撤回。** `--parallel 4` との比較は本件では未検証のままで、
リポジトリ既測 (B=2 58.15 / B=4 55.25) に依拠する。

→ いずれも「測定を信用する前に測定系を疑う」の再演。規約 4 の「外れたら続行せず
再診断」が両方とも機能した。
