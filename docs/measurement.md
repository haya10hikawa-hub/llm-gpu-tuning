# 測定の落とし穴と規約

この環境では、測定系の異常を対象の性質と誤認しやすい。実際に
「再帰状態の読み書きが decode の 36.6%」という診断を出し、それに基づいて
カーネル改修を 1 件実施して効果ゼロに終わった。クリーンな状態では 3.3% だった。

## 使ってはいけないツール

| ツール | 問題 | 実測 |
|---|---|---|
| `llama-bench` の tg 値 | 混合再帰アーキテクチャで実生成と乖離 | 8.59 vs 実測 24 (2.8倍) |
| `test-backend-ops perf` の GFLOPS | 23型中15型が PCIe 転送律速 | 19MB〜235MB の 12倍幅で逆算帯域が 10.4 ± 0.2 GB/s に固定 |

使うべきは `llama-completion` / `llama-server` の実生成、
`GGML_VK_PERF_LOGGER=1` の op 別 GPU 時間、正当性確認のみ `test-backend-ops test`。

## 環境由来の障害

| 事象 | 症状 | 原因 | 対処 |
|---|---|---|---|
| VRAM 断片化 | decode 24 → 14.5 t/s (-40%) | **プロセスの繰り返し起動・終了**で蓄積 | 対照を挟んで検出。常駐運用では起きない |
| GPU リセット | `Not enough memory for command submission` | 複数プロセスが同時に 13GB 超を確保 | 同時実行しない |
| DRM 権限喪失 | `No devices found` → 無言で CPU 実行 (0.85 t/s) | GPU リセットで `/dev/dri/*` が再生成され ACL 消失 | `sudo setfacl -m u:$USER:rw /dev/dri/renderD128 /dev/dri/card1` |

**CPU フォールバックは警告のみで進行する。** 検査しないと性能値として混入する。

## 作業上の事故

`pgrep -f` / `pkill -f` は**自分のコマンドライン**にマッチする。`echo` の
文字列にも当たる。本作業で 4 回自プロセスを kill した。

```bash
pgrep -f "bin/llama-comp[l]etion"    # OK
pgrep -f "bin/llama-completion"      # 自滅
```

`llama-completion` は生成後に対話モードへ移行して stdin を待つ。バッチ測定では
**`-st` と `< /dev/null` を必ず付ける**。付け忘れると timeout で殺され、
perf 出力に到達せず空値になる。

## 規約

1. GPU ジョブは常に 1 つ。起動前に `gpu_busy_percent` と `mem_info_vram_used` を確認
2. 全 run で `no usable GPU` を検査し、該当は破棄
3. 3 run ごとに対照構成を挟む
4. 変更前に反証可能な予測を書く。外れたら中断して再診断
5. 初回 run はシェーダコンパイル費用を含むので分けて扱う
6. **効果量の予測は実測値の範囲内に留める。** 外挿するなら外挿と明示する
7. **数値が動かないときは「効いていない」ではなく「飽和・クランプ」を先に疑う**
8. **「部分的に動いているように見える失敗」の検出条件を明示する**
9. **1 件の差を結論にしない。** カテゴリを広げて再現を確認する

## 規約 6〜9 が生まれた経緯

- **6**: 「純 K-quant で decode +22%」と外挿したが実測 +4.1%。
  「I/K で 8% 差」という実測を持ちながら加重平均が跳ぶと過大に見積もった
- **7**: `rm_iq` を振っても VGPR が 256 から動かず「効かない」と誤判断。
  実際はクランプされ、溢れがスクラッチへのスピルとして現れていた
- **8**: `prefill` は正常値 166 t/s を返すが `decode` が 0 だった。
  `curl -s` が HTTP 503 (ロード中) を成功扱いにした
- **9**: エージェント評価で n=1 の差を「低ビット量子化は引数を捏造する」と
  報告したが、カテゴリを広げたら再現せず撤回した
